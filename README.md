# ETWWPFApp

## 📖 Project Overview
`ETWWPFApp` is a WPF application demonstrating how to consume **Event Tracing for Windows (ETW)** to capture and analyze system-level telemetry. Built with `.NET 10`, this application showcases practical implementations of both real-time monitoring (**Live Sessions**) and offline analysis via **ETL file parsing**, specializing in tracing process lifecycle, thread behavior, and dynamic image/DLL loading events.

- **Target Framework**: `.NET 10.0`
- **Core Technology**: `Microsoft.Diagnostics.Tracing.TraceEvent`
- **Key Focus**: ETW Real-time Consumer Architecture, Multi-threaded Data Buffering, and Bounded WPF UI Updates.

---

## ✨ Key Features
- **Real-Time Live Session**: Captures live ETW events from a real-time session (Requires Administrator Privileges).
- **Offline ETL Parsing**: Parses offline `.etl` log files generated by standard diagnostic tools like PerfView or logman.
- **Granular Telemetry Tracing**:
  - **Process Lifecycle**: Tracks `ProcessStart`/`ProcessStop` with associated PIDs and Process Names.
  - **Thread Events**: Monitors `ThreadStart`/`ThreadStop` tied to their respective parent PIDs/TIDs.
  - **Dynamic Image Loading**: Captures `ImageLoad` events, identifying loaded modules, DLL names, and their Base Addresses in memory.

## 🚀 Usage & Workflow
1. **Live Monitoring Mode**  
   - Launch the application with **Administrator privileges** (mandatory for managing kernel ETW sessions).
   - Select the **Live** mode option and click **"Start Live"**.
   - The engine will dynamically stream live ETW events into the diagnostic dashboard.

2. **ETL Log Parsing Mode**  
   - Select the **From ETL** mode and click **"Open ETL"**.
   - Browse and select any standard `.etl` trace file (e.g., generated via PerfView).
   - The application will parse the binary trace sequentially and reconstruct the system event logs.

## ⚖️ UI Update Strategy
ETW produces many events, especially high-frequency ones like `ThreadStart/Stop` and `ImageLoad`, and dispatching each one to the UI thread would be costly. This project uses the following strategies to reduce the load on the UI thread. UI responsiveness before and after these changes was not measured:

- **Producer–consumer queue**: Utilizes a `ConcurrentQueue<T>` data pipeline to decouple the intensive background ETW consumer thread from the foreground UI rendering loop.
- **Batched UI Updates**: Replaced the original per-event `Dispatcher.BeginInvoke` calls (one dispatch per ETW callback) with a single `DispatcherTimer` ticking every 100ms. The timer batch-drains whatever has accumulated in `_eventQueue` since the last tick and applies it to the UI in one pass — no matter how many events arrive within that 100ms window, only one UI update is triggered.
- **Volatile Ring Buffering**: Caps the data visualizer (ListBox) at **2,000** displayed events. Once the limit is exceeded, the oldest items are evicted first (`Items.RemoveAt(0)`), keeping the visible log a fixed-size rolling window instead of growing unbounded. Validated across two independent test passes: a scripted batch of 150 rapid process start/stop cycles, and a ~15-minute idle background-noise soak test — in both, `Items.Count` plateaued at exactly 2,000 and did not continue climbing. Managed-heap size was also measured via `GC.GetTotalMemory(true)` (forcing a full collection before each sample) over a 13+ minute observation window; the value oscillated stably in the ~10–15MB range with repeated GC events pulling it back down, with no sign of unbounded growth in this observation.
- **Latency**: ETW delivers events with some buffering delay (about 1.3–1.6 s on average in the EtwCppConsumer project); the UI does not try to hide it.
